# Interactions: reinventing event workflows

Date: 2026-11-13
Status: approved in conversation, awaiting written-spec review
Replaces: `src/features/eventworkflows` (node-graph workflows)

## Intent

**What the user said.** Event workflows need reinventing for every reason at once:

- They are too complex to author.
- They are disconnected from the editor.
- They are not powerful enough.
- Saving them is fragile.

The primary users are low-code makers. The format must be friendly to three kinds of agent:

- an in-app AI assistant;
- external agents working through MCP or an API;
- coding agents reading generated code.

**Assumptions we agreed on.**

- One declarative format is the single source of truth. Every surface reads and writes it: the editor UI, agents, the runtime and codegen.
- The node-graph canvas is not part of v1.
- Existing workflows are migrated, not discarded.

**Success criteria.**

1. A maker can wire "on submit → call API → show toast / set variable" from the element's Inspector without opening a separate editor.
2. An agent can produce a valid interaction from a one-sentence request on the first try. It uses the published schema and `describe()`, and gets path-addressed errors when it is wrong.
3. Collaborators see interaction and logic edits live. Undo and redo cover interaction edits. Deleting an element removes its interactions, so no orphaned links are possible.
4. Concurrent edits to different interactions on the same element both survive.

## Problems with today's system

- **Two representations.** Each workflow is stored as `CanvasData` (the graph) plus `Handlers` (the compiled chain).
- **Separate storage.** Workflows sit in `EventWorkflow` and are linked through `ElementEventWorkflow`.
- **Unsafe saving.** Saves go over REST with last-write-wins, and collaborators are not notified live. The Go WS workflow handlers replace whole objects, broadcast only to the page room, and have no seq or ack. The client does not use them.
- **Orphaned links.** Deleting an element leaves its workflow links behind.
- **No undo.** Workflow edits are not covered by undo.

## §1 Data model

### Interactions on the element

Interactions live in `settings.interactions`, keyed by interaction id:

```jsonc
"settings": {
  "interactions": {
    "ix_7f2": {
      "on": "submit",
      "enabled": true,
      "do": [
        { "id": "signup", "call": "api", "method": "POST", "url": "/api/signup", "body": "{{ form }}" },
        { "if": "{{ steps.signup.ok }}",
          "then": [
            { "toast": "Welcome!", "kind": "success" },
            { "set": "user", "to": "{{ steps.signup.data }}" }
          ],
          "else": [{ "run": "showError" }] }
      ]
    }
  }
}
```

The interactions are a map keyed by id, not an array, because of how the realtime server merges element patches:

- `MergeMap` deep-merges `settings` and treats `null` as "delete this key". So a patch to `interactions.ix_a` does not touch `interactions.ix_b`, and two people editing different interactions on the same element both win.
- Deleting an interaction is `{ "interactions": { "ix_a": null } }`.
- Arrays are replaced whole. A `do` list is therefore last-write-wins per interaction, which is acceptable.
- The element create, update, move and delete ops, `diffTrees` undo sync, and delete cascades already carry `settings`. **No Go change is needed for element ops.**

**Interaction id:** `ix_` plus 8 random base36 characters, generated by the client.

**`on`:** one of the existing `EVENT_TYPES` (click, submit, change, hover enter/leave, focus, blur, load, and so on).

### Steps

A step is an object with exactly one **verb key**. It can also have an optional `id` (so later steps can read its result) and verb-specific fields.

| Verb | Shape (abridged) | Replaces action |
|---|---|---|
| `navigate` | `{ navigate: "/pricing" \| "https://…", newTab?, replace? }` | navigate |
| `show` / `hide` / `toggle` | `{ show: "<elementId>", duration? }` | show/hide/toggleElement |
| `scroll` | `{ scroll: "<elementId>" \| number, smooth?, offset? }` | scrollTo |
| `modal` | `{ modal: "open" \| "close", target?: "<elementId>" }` | modal |
| `toast` | `{ toast: "<text expr>", kind?, duration? }` | showNotification |
| `copy` | `{ copy: "<text expr>" }` | copyToClipboard |
| `download` | `{ download: "<url expr>", filename? }` | download |
| `animate` | `{ animate: "<elementId>", preset, duration? }` | animation |
| `class` | `{ class: "add" \| "remove" \| "toggle", target, name }` | toggleClass |
| `set` | `{ set: "<varName>", to: "<expr>" }` | setData |
| `call` | `{ call: "api", method, url, headers?, body?, timeout? }` | apiCall |
| `submit` | `{ submit: "<formElementId>" }` | form |
| `wait` | `{ wait: <ms> }` | handler `delay` |
| `if` | `{ if: "<expr>", then: Step[], else?: Step[] }` | condition / true-false handlers |
| `run` | `{ run: "<flowName>" }` | (new) reusable flows |
| `code` | `{ code: "<js>" }` | customCode (explicit escape hatch) |

There is no separate representation for modifiers. `preventDefault` and `stopPropagation` become optional booleans on the interaction itself.

### Expressions

Any string field may contain `{{ … }}`.

- **A string that is exactly one expression** evaluates to the expression's value, which keeps its type (object, number and so on).
- **Mixed text** is interpolated as a string.

**Scopes:**

- `vars.<name>`
- `event` (`event.value`, `event.checked`, `event.key`)
- `form` (the submitting form's fields as an object)
- `el.<elementId>` (`value`, `checked`, `visible`, `text`)
- `steps.<id>`

**Grammar:**

- literals
- property access (`.` and `[]`)
- `! && ||`
- `== != < <= > >=`
- `+ - * / %`
- ternary `?:`
- parentheses

There are no function calls, no assignment and no `eval`. Unsupported syntax is a validation error.

### Logic documents (variables and flows)

There are two levels, and both use the same shape:

- `Project.Logic` (new JSONB column) holds site-wide variables and flows.
- `Page.Logic` (new JSONB column) holds page-local variables and flows.

```jsonc
{
  "v": 1,
  "variables": {
    "user":  { "type": "object", "default": null,    "lifetime": "session" },
    "step":  { "type": "number", "default": 0,       "lifetime": "page" },
    "theme": { "type": "string", "default": "light", "lifetime": "local" }
  },
  "flows": {
    "showError": { "do": [{ "toast": "Something went wrong", "kind": "error" }] }
  }
}
```

**Variables:**

- `type` is one of `string`, `number`, `boolean`, `object` or `list`.
- `lifetime` is one of:
  - `page`: reset on each page load;
  - `session`: kept in `sessionStorage`;
  - `local`: kept in `localStorage`.
- Page-level variables default to `page`.

**One namespace.** Variable names are unique across the project document and every page document, and so are flow names. The validator rejects a collision.

- `vars.user` and `run: "showError"` therefore always resolve to exactly one definition. Agents never reason about shadowing.
- "Move to project" and "Move to page" change no references.
- Names match `^[a-zA-Z_][a-zA-Z0-9_]{0,63}$`.

### Validation

A single Zod schema, `features/interactions/schema.ts`, covers interactions, steps and Logic documents.

- At build time it is exported to `interactions.schema.json`, which agents and MCP use.
- Every write through `ops.ts` (see §4) is validated.
- Errors are path-addressed, for example `interactions.ix_7f2.do[1].url: required`.
- Cross-reference checks give warnings, not errors:
  - an unknown element id;
  - an unknown variable or flow;
  - `steps.<id>` read before that step runs.

## §2 Authoring in the editor

### Inspector "Interact" tab

The Inspector tabs become **Style | Settings | Interact**. The tab lists the selected element's interactions as readable sentences:

```
When  [Clicked ▾]                                   ⋯
  1  Call API  POST /api/signup  → signup
  2  If  signup.ok
       ├ Show toast  "Welcome!"
       └ Set  user  =  {{ steps.signup.data }}
     Else
       └ Run flow  showError
  + Add step
+ Add interaction
```

- **Add step** opens a searchable verb menu. Each step expands into a small form generated from its schema. Steps can be reordered by dragging and can be duplicated or deleted from the `⋯` menu.
- **Element fields** have a pick-from-canvas control. It stores the id and displays the element's name. A deleted target shows a "missing element" warning badge on the step.
- **Expression fields** autocomplete after `{{` with `vars.*`, earlier step ids under `steps.*`, `el.*`, `event.*` and `form`.
- Validation errors and warnings are shown inline on the step.
- Every change goes through `updateElement`, so undo, redo and collaborator sync need no extra work.
- Elements that have interactions show a small ⚡ marker in their canvas label.

### Logic rail panel

The rail's Workflows panel is replaced by **Logic**, which has two sections, **This page** and **Project**:

- **Variables:** name, type, default value and lifetime, with "used by" links that select the element.
- **Flows:** named step lists, edited with the same step editor.
- **Move to project / Move to page** changes no references.
- **Delete** warns when the item is still in use and lists where.

### Preview

- In edit mode, clicks still select. Interactions run only in Preview and on the published site.
- Preview shows a **run log** drawer. Each line has the event, the step path, the result or skip reason, and any error. This answers "why didn't anything happen?".

### Not in v1

- The node-graph canvas. A read-only flow diagram may come back later as a view.
- Binding variables into element content or attributes (`{{ vars.user.name }}` as text).

## §3 Runtime and codegen

### Interpreter (`features/interactions/runtime/`)

- **`evaluate(expr, scope)`:** a hand-written tokenizer and Pratt parser. Its parsed output is cached per expression string. It never uses `eval` or `new Function`, and property access blocks `__proto__`, `constructor` and `prototype`.
- **`run(steps, ctx)`:** runs steps in order, writes `ctx.steps[id]` for steps that have an id, and recurses into `if` and `run`.
  - `call` never throws. It stores `{ ok, status, data, error }`.
  - Any other failing step stops the current interaction and reports the step's path.
  - `run` has a recursion depth limit of 16.
- **Step executors:** a registry keyed by verb. The behaviour is ported from `features/editor/lib/events/eventExecutor.ts` onto the new step shapes.
- **Variable store:** a small reactive store per lifetime. `page` lives in memory, `session` in `sessionStorage` and `local` in `localStorage`. Every storage access is wrapped in try/catch and falls back to memory.
- **One runtime everywhere.** Preview and the published renderer share it. It is hooked in where `useElementEvents` is today, and that hook is replaced.

### Codegen

`toCode(project, pages)` emits readable TypeScript:

- one named async function per interaction (`onSignupButtonSubmit`), with a header comment naming the source element id and interaction id;
- flows as named functions;
- variables as one typed store module;
- expressions compiled to plain JS property access and operators.

It plugs into the existing code generation (`src/app/api/generate-code.ts`). The output is covered by snapshot tests.

## §4 Agent surfaces, sync, migration, errors, testing

### Operations module (`features/interactions/ops.ts`)

These are typed operations. Each one validates its input and then turns into store updates (element `settings` patches, or Logic ops):

- `addInteraction(elementId, on, steps)` returns the new id.
- `updateInteraction(elementId, ixId, patch)`
- `removeInteraction(elementId, ixId)`
- `setVariable(scope, name, def)` and `removeVariable(name)`
- `setFlow(scope, name, steps)` and `removeFlow(name)`
- `moveLogic(name, to: "project" | "page")`

Alongside them:

- **`describe(pageId)`** returns compact JSON: the element tree (id, name, type, child ids), each element's interactions, and the variables and flows in scope. This is what an agent reads first.
- **`interactions.schema.json`** is generated from the Zod schema.

The UI, the future in-app assistant (as tools) and a future MCP or API server all use this module. **Building the assistant and the MCP server is out of scope for this spec.** Each is its own later sub-project.

### Logic sync (realtime server)

The realtime server gets two new ops, `page:logic` and `project:logic`:

- **Payload:** a merge patch against the Logic document, with `null` meaning delete. It is applied with the existing `MergeMap`, so `flows.<name>.do` is replaced whole.
- **`page:logic`** runs on the existing page actor. It gets a seq, is acknowledged to the sender, and is broadcast to the page room.
- **`project:logic`** is serialized per project and broadcast to every connection in the project. Connections are already per project.
- **Validation:** the server checks the Logic document's shape and the uniqueness of names across levels. A rejection uses the existing error message path, and the client shows it with the existing toast and handling.
- **Initial load:** both documents are included in the page snapshot the client already requests.
- **Undo:** Logic edits are recorded in editor history. Undo sends an inverse merge patch, using the same approach as `patchWithDeletions`.
- **Persistence:** the API side gets a migration adding `Logic` JSONB (nullable) to `Project` and `Page`.

### Migration of existing workflows

The migration is a one-off command in the Go API repo. It has `--dry-run` by default and `--apply`.

1. For each `ElementEventWorkflow` link, translate the workflow's compiled `Handlers` into steps.
   - `trueHandlers` / `falseHandlers` become `if` / `then` / `else`.
   - `delay` becomes `wait`.
   - Each action config maps onto the verb in the §1 table.
2. If a workflow is linked from one element, write an interaction to that element's `settings.interactions`. If it is linked from several elements, create a page flow (or a project flow when the elements are on several pages) and give each element `{ run: <flow> }`.
3. Report everything that could not be translated, with the workflow id and the reason. Nothing is silently dropped.
4. The `EventWorkflow` and `ElementEventWorkflow` tables stay read-only for one release and are dropped after that.
5. The following are removed:
   - `src/features/eventworkflows`;
   - `features/editor/store/event-workflow-store.ts`;
   - the workflow server functions;
   - the Go WS `workflow_handlers.go`.

### Errors

- **Validation:** path-addressed errors are shown inline in the editor and returned verbatim to agents.
- **Dangling references** (an element, variable or flow that does not exist):
  - the editor shows a warning badge;
  - at runtime the step is skipped and a warning is logged to the run log or console.
- **Rejected Logic ops:** handled through the existing rejection path. The local change is rolled back and a toast is shown.

### Testing

**Unit tests (node:test with tsx):**

- the schema: valid and invalid cases, and name collisions across levels;
- the evaluator: the grammar, precedence, type preservation, and hostile input (`__proto__`, deep nesting, very long input);
- the interpreter: ordering, `if` branches, `call` results, failure stops, `run` depth limit, dangling references;
- the variable store's lifetimes;
- `ops` and `describe`;
- codegen snapshots;
- migration fixtures built from real `Handlers` shapes.

**Integration tests (`bun run test:integration` against the real realtime server):**

- concurrent edits to different interaction ids on one element both survive;
- `page:logic` and `project:logic` broadcast and acknowledgement;
- undo of an interaction edit reaches the other client.

**End-to-end:** none in v1, because of the Clerk constraint. To be added once a non-interactive auth path exists.

## Build order

1. Schema, evaluator, interpreter and variable store (pure; unit tested).
2. `ops.ts`, `describe`, the Interact tab, runtime wiring, and the Preview run log.
3. The `Logic` columns, the `page:logic` and `project:logic` server ops, and the Logic panel.
4. Codegen.
5. Migration, then removal of the old feature.
6. Later sub-projects, each with its own spec: the in-app assistant, then the MCP server.

## Out of scope

- The node-graph canvas.
- Binding variables into content.
- The in-app assistant and the MCP server.
- Triggers that are not element events (timers, page lifecycle beyond `load`, webhooks).
- Server-side execution of interactions.
